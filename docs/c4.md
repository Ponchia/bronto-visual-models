# C4 architecture

The C4 family is included in the published beta.6 archive.
The `c4` family owns architecture semantics and a dedicated interactive renderer.
It is not an interchangeable graph/matrix/network preset.

## Implemented diagrams and semantics

The first slice implements system landscape, system context (C1), container (C2)
and component (C3) diagrams. People and software systems are top-level elements;
containers belong to a software system, and components to a container. Here,
container means a C4 application or data store, not specifically a Docker container.

Each element has an identified name, type and responsibility. Containers and
components require technology. Relationships are directed, labelled records with
optional protocol and description. Missing container-to-container protocol is an
advisory, not an invented value. Duplicate IDs, absent endpoints, invalid parents
and incompatible diagram scopes are refused before a commit.

Named diagrams explicitly include elements at their abstraction level. Context
includes its system; container and component scopes appear as boundaries instead
of duplicated cards. Component diagrams can include sibling containers from the
same system. Supporting people and external systems can appear at those levels.
An explicit `relationshipIds` list restricts relationships; otherwise only authored
relationships whose endpoints are both included are drawn. An empty list means
none. There is no inferred relationship roll-up or silent level conversion.

## Create, inspect and edit

```ts
import { MemoryModelStore } from "@ponchia/visual-models";
import { c4Scene, c4RecordEdit } from "@ponchia/visual-models/render/c4";

const store = new MemoryModelStore();
await store.execute({
  type: "create",
  key: "create-commerce",
  model: { id: "commerce", title: "Commerce architecture", template: "c4-commerce" },
});
const model = store.get("commerce")!;
const patch = c4RecordEdit(model, "elements", "api", { label: "Checkout API" });
const command = { type: "edit" as const, key: "rename-api", id: model.id, patch };
const preview = await store.preview(command);
// Review preview.model and preview.changes before committing.
await store.execute(command);
```

`C4Content`, `C4Element`, `C4Relationship`, `C4View` and the schema are exported
from the core and `/c4`. `c4Scene` takes validated C4 content and a named diagram
ID. It returns only that diagram's elements, authored relationships and boundary.
Unknown IDs refuse rather than substituting a different diagram.

`elements`, `relationships` and `views` use normal model targets, incarnations,
search, preview, receipts and undo. The new family has renderer version 1; the
existing model envelope remains version 2. An older build that does not know C4
must preserve its bytes and refuse interpretation.

## Purpose-built reference renderer

`VisualModelView` selects the lazy C4 renderer for this family. It provides typed
cards with responsibility and technology, a separate external notation, directed
relationships with protocol labels, explicit scope boundaries and a legend.
Database and queue symbols are optional element shapes. Card text is bounded for
legibility; the inspector and semantic Read data mode retain full text.

Choose a named diagram or select a system/container and open its scoped diagrams
from the inspector. Find an element by name, responsibility or technology, then
focus it without filtering the architecture away. Relationships have their own
keyboard-selectable chooser, including parallel relationships. Pan, zoom,
selection, search and drill-down are local presentation, not stored model edits.
Canvas resizing keeps the selected element wholly visible, zooming out when the
canvas is smaller than its card; without a selected element, it fits the current
diagram. Typing or receiving a model edit does not refit it.

A host can control navigation with `c4ViewId` and `onC4ViewChange`. Without the
callback, a supplied view ID is read-only navigation. An unavailable controlled
ID is shown as unavailable, not replaced by the first diagram. Omit both to use
local navigation. The host controls selection when it supplies `selected`.

A host that already loads React Flow's stylesheet, such as a React Flow canvas
that embeds model views in its nodes, imports `@ponchia/visual-models/base.css`
and `@ponchia/visual-models/c4.css` instead of the aggregate `styles.css`, which
would apply React Flow's defaults again. The C4 flow checks its own
`bvm-c4-nodrag`, `bvm-c4-nopan` and `bvm-c4-nowheel` gesture guards, so a host's
default React Flow guards on ancestor elements do not disable its wheel zoom or
pane drag.

With `onEdit`, the inspector edits details and dragging saves positions for the
current named diagram only. Arrow keys on a focused element move it by 10 units;
Shift increases the step to 50. Read-only and inactive views do not issue writes.
Reset diagram layout clears only that diagram's positions. These operations
retain model generation and revision preconditions, including against replacement
of an element with the same ID. A dirty inspector draft keeps its original base
when another writer commits; reload it explicitly after a conflict.

The host must commit the patch and pass back the new model. Synchronous and
asynchronous refusals restore current host geometry, not an obsolete drag snapshot.
An accepted callback alone is not proof of durable storage. See [storage](storage.md).

## Deliberate limits

This slice does not implement code-level (C4), dynamic or deployment diagrams,
Structurizr DSL/JSON import, C4-PlantUML round trips, or a code scanner. There is no
claim of complete Structurizr compatibility. Those deserve dedicated models and
acceptance cases, not lossily accepted fields. Unknown diagram kinds are refused.

The renderer uses the existing optional React Flow peer. It adds no runtime
package, remote compiler, icon URL, network request or executable source.
Default positions are deterministic, not an optimal graph-layout claim. Dense
architecture may need manual arrangement; arbitrary label collision avoidance,
SVG/PNG export is not implemented here. Optional [C4 layout previews and routing](c4-layout.md)
are now available with a host-owned worker. No export
capability is advertised. The existing graph layout helper remains separate.

A model admits 1,000 elements, 2,000 relationships and 64 diagrams; each diagram
admits at most 300 elements. Existing whole-model JSON limits still apply. These
are admission limits, not a measured smooth-rendering guarantee at the maximum.

Removing a referenced element without fixing its descendants, relationships or
diagrams is refused atomically. Update those references in the same edit; no
complete diagram is silently deleted as a cascade convenience.

## References and verification

The semantics follow the official [C4 diagram types](https://c4model.com/diagrams),
[notation guidance](https://c4model.com/diagrams/notation) and
[component scope](https://c4model.com/diagrams/component). The sample commerce
architecture is original illustrative data, not a copy of the official diagrams.

`test/c4.test.ts` covers structural refusals, view boundaries, identity, preview,
replay, undo, restart and stale edits. The independently installed packed browser
fixture covers navigation, full text, controlled edits, keyboard layout, refusal
recovery, read-only/hidden behavior and automated accessibility. It joins the
Chromium/Firefox/WebKit CI matrix. Passing checks is not manual screen-reader
certification or qualification of a Spatial upgrade.
